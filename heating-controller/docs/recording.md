# SQLite recording

The optional recorder writes schema version 1 (`PRAGMA user_version`). Unknown
versions and nonempty unversioned databases are rejected without migration.
Failures are reported through logging and, when enabled, Home Assistant room
diagnostics. Recording is local; no device commands or unrelated MQTT traffic
are generated by the recorder.

## Common event columns

Every table except `runs` has:

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | INTEGER PRIMARY KEY | Database row identity |
| `run_id` | INTEGER | Foreign key to `runs` |
| `event_key` | INTEGER, nullable | Internal queue correlation key, unique within a run and table |
| `recorded_at_utc` | INTEGER | Receipt/evaluation time as UTC Unix milliseconds |
| `elapsed_seconds` | REAL | Monotonic seconds since this run began |
| `room_id` | TEXT, nullable | Configured room ID; null for controller-wide events |

Wall-clock corrections do not affect monotonic elapsed times. Sensor receipt
time does not establish physical measurement time. There are indexes on
`(room_id, recorded_at_utc)`, correlation keys and each foreign-key reference.
Missing values are SQL NULL. Database IDs, rather than queue keys, are used in
foreign-key columns. The writer resolves links within their own run; a lost
parent record leaves a null reference, never a link to a different run.

## Tables

### `runs`

`id`, `started_at_utc`, `ended_at_utc`, `software_version`, `git_revision`,
`working_tree_dirty`, `dry_run`, `config_json`, `stop_reason`, `dropped_records`.

The configuration is the effective configuration after CLI overrides, including
room gains and schedules. MQTT credential environment names and their values are
not recorded. Git metadata is best-effort; packaged installations may have no
revision. A dirty flag indicates that a commit alone cannot reproduce the code.
Run-level times use UTC milliseconds. A crash leaves `ended_at_utc` null.
Database failure also leaves the run incomplete, with `recording_failure` as the
stop reason if writing that final status is still possible.

### `temperature_readings`

`topic`, `temperature_c`, `value_changed`, plus common columns.

Every accepted non-retained temperature arrival is recorded, including repeated
values. Invalid, humidity-only and retained messages are not accepted readings.
`value_changed` is true for the first reading following startup/reconnect.

### `control_samples`

`temperature_reading_id`, `temperature_c`, `target_temperature_c`,
`measurement_age_seconds`, `supply_available`, `heating_requested`,
`control_status`, `proportional_percent`, `integral_percent`,
`requested_opening_percent`, `saturated`, `actuator_phase`, `actuator_fault`,
plus common columns.

One row per room evaluation. Schedule fields describe configured availability,
not boiler feedback. PI fields are the contributions used for that evaluation,
before any subsequent actuator-related integration reset. Actuator fields are
updated after processing the evaluation. They can briefly be null during a
concurrent read, or remain null if that update was dropped or the process crashed.
Zero requested opening is recorded when inhibited; absent PI terms remain null.

### `actuator_commands`

`control_sample_id`, `command_topic`, `payload_json`, `reason`, `outcome`,
`completed_at_utc`, `confirmation_report_id`, `failure_reason`, plus common columns.

Outcomes are `pending`, `confirmed`, `simulated`, `failed` or `superseded`.
Commands issued for shutdown have no originating control sample. Identical
retries stay attached to one command. Recomputing a retry with a different payload
supersedes the old command and creates a new one, with its own exact payload.
The coordinator's existing overall retry limit still applies.

Confirmation means that the coordinator observed matching, post-command device
reports. Several partial reports can contribute to a match;
`confirmation_report_id` points to the latest report in the snapshot completing
that match. Inspect earlier reports in the same connection generation to
reconstruct it. Simulation never creates a confirmation report. Neither MQTT
publication nor reported settings prove motor movement or physical water-flow
closure.

### `command_attempts`

`command_id`, `attempt_number`, `connection_generation`, `send_result`,
`mqtt_return_code`, `error_message`, plus common columns.

Each send/retry has a row. `sent` means the MQTT client accepted publication;
`rejected` indicates refusal or transport failure; `dry_run` means simulated.
The MQTT return code is null when no MQTT publication was attempted. Attempt
numbers start at one for each logical command. A missing command reference can
indicate recording loss; consult run/recording-gap diagnostics.

### `valve_reports`

`topic`, `payload_json`, `retained`, `accepted`, `rejection_reason`,
`connection_generation`, `report_sequence`, `opening_setting_percent`,
`closing_setting_percent`, `system_mode`, `running_state`,
`external_temperature_c`, `setpoint_c`, plus common columns.

The original payload is preserved as text (malformed payloads need not be valid
JSON; invalid UTF-8 bytes are replaced for storage). Retained, malformed and
unavailable-device reports are recorded as rejected, without confirming commands.
Accepted reports contain per-message parsed fields; missing/invalid fields stay
null and are never silently filled from earlier reports. Ignored reports have
unparsed control fields. `running_state` is extracted only when it is `idle` or
`heat`. A report accepted for reconciliation can still invalidate individual
fields. Device opening/closing settings are not measured valve position.

### `events`

`event_type`, `severity`, `source`, `message`, `details_json`, plus common columns.

Events cover connection changes, valve availability, applied target changes,
room control/actuator transitions, integration reset/zeroing, shutdown, recording
gaps and annotations. An integral returning to zero may be arithmetic unwinding;
`integration_zeroed` does not claim a forced reset. Target changes explicitly
record an `integration_reset` event. `details_json` carries structured context.

Application integrations can add annotations through the recorder API:

```python
recorder.annotate("Artificial sensor heating", room_id="bedroom",
                  start_at_utc=1791478800000, end_at_utc=1791479400000)
```

Times in this example are placeholders; use actual experiment times. This API
queues an event through the existing writer. There is no MQTT annotation command
or standalone annotation CLI yet.

## Failure and retention behavior

The queue is bounded by operation count. `dropped_records` counts lost insert
**and update** operations, not necessarily distinct rows. Overflow is latched as
a recording fault for the run; recording continues as capacity becomes available.
A gap event and cumulative run counter are persisted when the writer can do so.
Database errors stop the writer; later dropped-operation counts remain visible
in memory/HA but cannot be guaranteed durable when the database is unavailable.
Control and sensor processing continue. Restart to retry a failed writer.

The writer batches up to 100 operations, normally committing within the configured
flush interval. Shutdown drains the queue with a five-second wait limit. A crash
or forced termination can lose queued/uncommitted data; this is an analysis
recorder, not a durable command journal. Rows may retain `pending` outcomes after
recording loss or a crash. Do not interpret them as success.

Completed runs ending more than `retention_days` ago are deleted at startup and
hourly. Current/incomplete runs are preserved, including crash investigations.
A continuously running process can therefore retain more than the configured
window. Foreign keys cascade deletion across all seven tables. No automatic
VACUUM is performed. Use SQLite's backup API for a consistent live backup rather
than copying only the main database file while WAL is active.

## Analysis examples

Temperature, target and demand for one room:

```sql
SELECT datetime(recorded_at_utc / 1000.0, 'unixepoch') AS utc,
       temperature_c, target_temperature_c, requested_opening_percent,
       proportional_percent, integral_percent, control_status
FROM control_samples
WHERE room_id = 'bedroom'
ORDER BY recorded_at_utc, id;
```

Command attempts and outcomes (filter `runs.dry_run = 0` for actual publication):

```sql
SELECT c.id, c.reason, c.payload_json, c.outcome,
       a.attempt_number, a.send_result, a.mqtt_return_code,
       c.confirmation_report_id
FROM actuator_commands AS c
JOIN runs AS r ON r.id = c.run_id
LEFT JOIN command_attempts AS a ON a.command_id = c.id
WHERE c.room_id = 'bedroom' AND r.dry_run = 0
ORDER BY c.id, a.attempt_number;
```

Sensor arrival gaps, with run boundaries kept separate:

```sql
SELECT run_id, room_id, recorded_at_utc, temperature_c,
       elapsed_seconds - lag(elapsed_seconds) OVER (
           PARTITION BY run_id, room_id ORDER BY id
       ) AS gap_seconds
FROM temperature_readings
ORDER BY run_id, room_id, id;
```
